# worldTraveler Workspace: Guide for AI and Developers

This is a **worldTraveler (psyl)** workspace: the frontend uses an in-house TypeScript + Vue 2.7 framework, and backends can mix .NET 10, Python 3.14 and Go 1.27.
The tool command is `wt` (the right-click menu of the "worldTraveler" VS Code extension calls the same commands).

> The extension and wt show Chinese when VS Code / the system language is Chinese or Japanese, and English otherwise.

## Layout

```
worldtraveler.json         workspace settings (name, docker network, frontend core fallback)
.worldtraveler/            workspace key (not under version control)
src/                       frontend source
  config/                  shared entry area: loadModel.ts (load order), public.ts, InterfaceJsonHost.json (backend API hosts)
  models/                  shared extension components (js / css / ts models) and SDK types: vueSDK.ts, vueTemplateFormat.ts, SysConfig_Interface/
  <project>/               frontend sub-projects (e.g. init, aa): main.ts, main.html, main_VueTemp.ts, main_Interface.ts,
                           view/, controllers/, temp/, model/, package.json (bundle list), tscpackage.json (TS models)
extendsComponent/          custom Vue components (.vue: <template> + <script lang="ts"> + <style lang="scss">)
Libary&Document/libary/    images (bundled as importLoad.img['folder'])
Libary&Document/jsonDoc/   i18n / settings JSON (bundled as importLoad.m.json['folder_filename'])
dir/                       bundle output = site wwwroot (dir/libjs/*); don't edit by hand
DotNetProject/             .NET 10 backends (the ConfigForSystem shared library lives here)
PythonProject/             Python 3.14 backends
goProject/                 Go 1.27 backends
.vscode/launch.json        Docker debug configs for each backend (generated by wt)
docker-compose.yml         frontend debug + nginx gateway + Redis + backend API services (the api-* block is maintained by wt)
nginx/                     gateway config: default.conf, routes/<API name>.conf (generated by wt)
.env                       compose parameters: WT_PROJECT (includes the workspace id), WT_NETWORK, WT_PORT, COMPOSE_PROFILES, keys
```

## Frontend Framework Conventions (Important)

> **⚠ Required reading: before editing `src/` or `extendsComponent/`, read [`createVueRule.md`](createVueRule.md)** (entry points, MVVM layering, lifecycle, how to write each layer, `<json>` text sets, `<totemp>` nested templates, `ajax` API calls, `task` async flows, wtd i18n, src/models plugin packages, main / companion file naming, checklist), and when done, check your work against its §13 checklist. The following is a summary.

- **Import the SDK only from `src/models/vueSDK.ts`**: `vueComponentModel`, `vueModelControllers`, `Component`, `task`, `pb`, `ajax`, `sleep`, `importLoad`, `MainVueTemplate`, `VueTemplate`. These are type wrappers around runtime global objects; don't turn them into npm packages.
- **New pages**: right-click in VS Code → "New Frontend Page...", or `wt fe new view <project> <name>` (view), `wt fe new doc <project> temp/<path>.html` (template component).
- **One view = four files with the same name**: `view/X.ts` (Vue component definition), `view/X.html` (template), `view/X.scss` (styles, optional), `view/X_Interface.ts` / `X_VueTemp.ts` (types).
  `controllers/X.ts` holds data and events. Create new views with `wt fe new view`, which also updates `package.json`.
- **Component object format**: `export default { data:{...}, init:($t)=>{}, temp:($t)=>({...}), completed:($t)=>{} } as vueComponentModel<Data, VueTemp>`
  - `$t` is the component instance (equivalent to Vue's `this`) and carries loaders such as `$t.import.url('@view/index')`.
  - `temp` returns the sub-templates to mount; pass data in with `.exportVue({...})`.
- **Frontend core version**: `.toVueVersion("vue2" | "vue3" | "auto")` in `src/init/main.ts` selects the core, and the output syntax follows the core (vue2 = ES5, vue3 = ES2020). `auto`: debug uses vue2 (with a console notice); release builds `dir/libjs` (vue2) and `dir/libjs3` (vue3), and the middleware `CoreSelect` picks one per browser (detect / ua); write code to vue2 rules (createVueRule.md §1.1.1). Don't set a target in tsconfig, `worldtraveler.json` or `.env`. For sharing one codebase across both cores, see createVueRule.md §1.1.1.
- **Arrow functions**: write them as usual (vue2 compiles them to ES5 regular functions; the vue3 core doesn't call user functions with `new`).
- **Special HTML template tags** (see createVueRule.md §8, §9):
  - `<json map="tw.panel">{...}</json>` or `<json map="tw" src="lang/tw.json"></json>`: text sets / translations / static data, read with `$t.getJson("tw")`; deep-merged within a component
  - `<totemp content="param">relative-path.html</totemp>`: expands a sub-template at bundle time (can be nested); the path is relative to **the html file containing this tag**; `@v{content}` in the sub-template is replaced by the parameter (the legacy `@>content<@` still works but contains `<`; use `@v{}`; the bundler warns when no value is passed); attributes such as `v-if` / `class` / `tag` go on the wrapper
  - `<totemp props="x.json" idx="0">item.html</totemp>`: generates repeated items from a json array; the sub-template uses `@v{[idx].field}` (index name in lowercase)
  - `<bundle>true</bundle>`: in release, embeds the template directly in the JS instead of producing a separate t*.txt (only for small, always-shown templates; measure first — createVueRule.md §9.5)
  - `<script>` / `<style>` are extracted and merged into the JS / CSS respectively; `<script lang="ts">` (or `src="./X.script.ts"`) is compiled by TypeScript together with the views (imports at the top); inside it, `$view` gives the same-named .ts's export default (`$view.vue`) and the component `$t` (`$view.created / ready / leave`)
- **Load order**: `src/config/loadModel.ts` decides the load order (shared css → public → entry sub-project `$t.p.init`).
- **Site-wide shared settings (createVueRule.md §1.3)**: `src/config/public.ts` builds `importLoad.pub` (`config.get("title")` reads `jsonDoc/config/<lang>.json`, `libSrc('x.png')` reads images from `libary/pub`); when adding fields, update `config/interface/publicObjec_Interface.ts` too. pub holds only settings / images / helper functions that don't change after loading; it is not reactive data.
- **Prefer `<totemp>` for splitting files (createVueRule.md §9.6)**: an .html embeds another .html directly, without creating another Vue component, sharing the parent's data, with no exportVue copies or load-timing issues; split into a child component only when it needs its own lifecycle / async loading.
- **Calling backend APIs**: always use **relative paths** `/<API name>/...` (e.g. `ajax.Form.Get("/OrderApi/env/test")`), forwarded by nginx: same origin, no CORS needed (see "Frontend and Backend on One URL" below).
  `src/config/InterfaceJsonHost.json` is only used by `wt fe tscdb` to fetch DB structures.
- **API calls (createVueRule.md §10)**: use `ajax.Form.Get` for GET (`ajax.JSON` has no Get); every call needs `.Catch` (without it, non-200 responses are retried 3 times automatically and nothing happens on screen); business errors come back from the backend as 200 + `Ok:false`.
- **Async flows (createVueRule.md §11)**: `task.Factory.StartNew(...).ContinueWith({SuccessEvent})...ContinueCatch(...)`; every step must call `o.resolve` / `o.reject`, and long tasks should `Abort()` when leaving.
- **i18n (createVueRule.md §8.4)**: put text in `temp/translation/<lang>/<document>.json` and read it with `wtd.doc($t,"document")` (`src/config/wtd.ts`); every language must have the same structure as the default language (wt checks this).
- **Plugin packages (createVueRule.md §12)**: js packages go in `src/models/<name>/` (main.js defines a global variable with the same name + interface.ts) and are lazy-loaded with `$t.import.m.js.<name>(e=>e()...)`; small shared helpers are written as `.ts` and imported directly.
- **Elements, events and scrolling (createVueRule.md §4.4.1)**: always use `pb.el`: `pb.el.win.on("scroll", f, { owner:$t, throttle:"frame" })`, `pb.el.doc.on(…)`, `pb.el.id("x").on("click", (el, e)=>…)`, `off`, `outside`, `delegate`, `pb.el.q / qa`, `.scrollTo({ offset })`, `.rect()`, `.cls`, `.attr`; do not write `addEventListener`, `removeEventListener`, `getElementById`, `querySelector` or `scrollIntoView` directly. `pb.el.id(x).get` may be `null`; check `.exist` first.
- **TS models (createVueRule.md §12.3)**: business processes: `wt fe new tsc <project> model/<name>` → controllers `discreteModelLoad:{ $m:M.model_<name> }`; site-wide TS packages: `wt fe new tsc models <name>` → `$t.import.m.js.<name><T>(C=>new C($t))`. Loaders return a Promise, so inside an async action you can write `const C = await $t.import.m.js.<name><T>()` (sub-project: `await $t.import.p.<project>()` returns insert). For both, **take types only with `import type`** (a regular import bundles the code into the project). The VS Code right-click menu has "New TS Model (Business Logic)..." and "New TS Package (models)...".
- **Concatenation order for multi-file models**: add `"order": ["core.js", ...]` to `src/models/<name>/<name>.json`.

## Backend Conventions

Projects in every language use the same structure:

| Folder | Purpose |
|---|---|
| `Config/` | Environment settings |
| `Domain/` | Procedural functions |
| `Models/` | Business features at runtime |
| `Repositories/` | Static data, interfaces, data formats |

- **.NET**:
  - Reference `DotNetProject/ConfigForSystem` with `ProjectReference` (JObj, JwtHelpers, DB migration, Redis, CacheMemoryService).
  - The frontend injection component is a dll: `DotNetProject/worldTravelerVueMiddleWare/worldTravelerVueMiddleWare.dll` (copied automatically by `wt new dotnet webapi`; the csproj references it via HintPath). A webapi's `Startup` calls `services.AddWorldTravelerVue()` and `app.UseWorldTravelerVue(Configuration)` (which also loads the key WorldTraveler:TscPassword).
  - Add or remove projects with `wt`, which keeps `<workspace>.sln` and `.slnx` in sync.
- **Python**: the Flask factory is in `app.py`, routes go in `Models/routes.py` (Blueprint), settings in `Config/config.json`, overridable with `WT_<KEY>` environment variables.
- **Go**: standard library `net/http` only (Go 1.22+ routing). Routes go in `Models/`, Redis / cache helpers in `Domain/`, settings in `Config/config.json`.

### Which language to use (decide before adding a backend feature)

| Language | Use for | Examples |
|---|---|---|
| .NET | Large, multi-person teams; high data-correctness requirements, heavy computation or load | Orders, payments, members, reports, scheduling |
| Python | Data validation and unit tests, scraping and data parsing, generating images or video in memory | Validation scripts, scrapers, report charts, thumbnails, image processing |
| Go | Features that need protection by packaging (compiled into a single binary: callable but not modifiable), subprograms for other projects, long-running listeners | Encryption, license checks, file / queue listeners, background services |

## Frontend and Backend on One URL (nginx Gateway + Docker Debug)

```
Browser ──▶ nginx :WT_PORT (.env)
             ├─ /                 → web   frontend (dir/)
             ├─ /wsBundleDebugLog → web   auto-reload on save
             └─ /<API name>/xxx   → <API name>.api/xxx   (nginx/routes/<API name>.conf, prefix stripped)
                                     ├ the debug container from VS Code F5 "Docker <language>:<name>"
                                     └ or the compose service api-<name> (profile api, when not debugging)
All containers are on the same docker network (network in worldtraveler.json = WT_NETWORK in .env = dockerRun.network in tasks.json)
```

- **Adding an API**: `wt new <language> webapi -o <name>` (or right-click). wt does it all at once: the project, `.sln`, launch/tasks, the `api-<name>` service in `docker-compose.yml`, and `nginx/routes/<name>.conf`. **Don't copy these settings by hand**; use `wt remove` to remove them.
- **Debugging an API**: in VS Code Run and Debug, pick "Docker <language>:<name>" → F5. preLaunch first runs `docker compose stop api-<name>`, then starts a debug container with the same hostname `<name>.api`; nginx re-resolves DNS on every request, so no restart is needed.
- **Running all APIs without debugging**: `docker compose --profile api up -d --build` (or right-click DotNetProject → worldTraveler → Run All Backend APIs in Containers (No Debug)).
- **Calling from the frontend**: `ajax.Form.Get("/OrderApi/xxx")`. API-side routes **don't include** the prefix (`/OrderApi/env/test` reaches the API as `/env/test`). To change the prefix (e.g. `/api/order/`), edit `nginx/routes/<name>.conf`, then run `docker compose exec nginx nginx -s reload`.
- **APIs calling each other**: inside containers, use `http://<name>.api/...` directly (bypassing nginx).
- **Redis 7.4**: set `COMPOSE_PROFILES=redis` in `.env` (or right-click "Enable / Disable Redis 7.4"); the hostname inside containers is `redis:6379`; the local port is random, look it up with `docker compose port redis 6379`. Use `redis` as the Redis host in backend settings.
- **No name collisions**: the compose project name `WT_PROJECT` = workspace name + a 6-character id (e.g. `myshop-3f9a1c`), and containers, networks, volumes and debug images all use it as a prefix; install.sh picks a site port that isn't already in use. **Don't hard-code `container_name` in docker-compose.yml**, and don't hard-code host ports other projects may use.
- Example: `nginx/routes/TourApi.conf` forwards `/TourApi/` to `TourApi.api`, and the frontend calls `ajax.Form.Get("/TourApi/tours")`.

## Commands

```bash
wt new dotnet|python|go webapi|console[|classlib] -o <name> [-p <port>]   # backend project + Docker debug config
wt remove <language> <name> --yes
wt fe build                           # frontend release bundle → dir/libjs (core / syntax follow toVueVersion in main.ts)
wt fe debug --notify http://web       # frontend watcher; the browser reloads about 1 second after saving
docker compose up -d                  # frontend debug (web + bundle + nginx), open http://127.0.0.1:<WT_PORT from .env>
# Message language: WT_LANG=zh | en in .env (install.sh sets it from the system language; the extension follows the VS Code language; Chinese / Japanese → Chinese, others → English)
# Frontend mode: WT_FE_MODE=debug | release in .env, then run docker compose up -d bundle (one-click toggle via "wT debug / wT release" in the VS Code status bar)
docker compose --profile api up -d --build   # run all backend APIs in containers (no debugging)
docker compose exec nginx nginx -s reload    # reload after editing nginx/
```

## Notes for AI

- **Choose the language first when adding a backend feature** (see "Which language to use" above): if the user didn't specify one, choose by the nature of the work and explain why; if the workspace already has an API of the same kind, add to that existing project rather than creating a new project or switching languages for a small feature.
- Don't put core business logic (amounts, inventory, permission checks) in Python scripts or the frontend; put calculations that must be correct in the .NET `Domain/`.
- When Python generates images / video, process them in memory and return them directly (base64 or a stream); don't write them to the container file system. Scrapers must set timeouts and retry limits.
- When Go is used for encryption or subprograms called by other projects, read keys from settings or environment variables, never hard-code them in source; expose only the routes that are needed.
- The three languages use different response formats (.NET uses PascalCase `Ok / Data / Message`, Python / Go use lowercase); match each service when writing frontend types.
- Don't modify `dir/` (bundle output) or generated files other than `DotNetProject/ConfigForSystem` unless the task explicitly requires it.
- Don't convert the frontend to a webpack, vite or npm package structure; this framework relies on the `inputFiles` list in `package.json` and `wt fe` bundling.
- Backend debugging always happens in Docker (`.vscode/launch.json`). Ports, container names, hostnames, compose services and nginx routes for new projects are all assigned and generated by `wt`.
- Don't hard-code API URLs like `http://127.0.0.1:5001` in the frontend; use relative paths `/<API name>/...`.
- The `# >>> wt:api` … `# <<< wt:api` block in `docker-compose.yml` is maintained by wt; add other services (DB, MQ…) outside that block, attach them to `networks: [workspace]`, and don't set `container_name`.
